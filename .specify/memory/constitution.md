# 개미비서단 Constitution

이 문서는 개미비서단에서 **무엇을 기준으로 만들고, 어떤 기준으로 PR을 리뷰·승인하는지** 정합니다.
팀원 3명과 AI 에이전트가 같은 기준으로 판단하는 것이 목적입니다. 이 방식은 Spec-Driven Development(SDD)의
spec-anchored 방식입니다. 명세를 먼저 쓰고, 기능이 바뀌면 명세도 함께 고칩니다.

## Core Principles

### I. 명세가 기준이다 (Spec-Anchored)

- 모든 기능 PR은 기준 명세에 연결되어야 합니다(MUST).
  - 사용자 기능: 기능 명세서의 FN-ID와 인수 조건
  - 에이전트 내부 동작: 에이전트 기획서의 해당 절 또는 `specs/<번호>-<이름>/spec.md`
  - 데이터·인터페이스: `docs/api/openapi.yaml` 또는 `docs/decisions/`의 ADR
- 코드가 명세와 다르면 같은 PR에서 명세를 고치거나, ADR을 먼저 써야 합니다(MUST).
  명세를 고치지 않은 채 명세와 다른 코드는 머지하지 않습니다.
- 명세 PR은 그 명세를 구현하는 PR보다 먼저 머지합니다(MUST).

근거: SDD에서 가장 흔한 실패는 코드만 바뀌고 명세가 남겨져 명세가 기준 역할을 잃는 것(spec drift)입니다.

### II. 계약 우선 (Contract-First)

- 팀 경계의 인터페이스는 `openapi.yaml`과 공용 열거형(`AgendaId`, `DataTier`, `Tier`, `ReasonCode` 등)이 기준입니다.
  같은 값을 문자열로 다시 쓰지 않고 import합니다(MUST).
- 데이터가 제공하는 계약은 data-pipeline에, backend 내부 계약은 `backend/contracts/`에 둡니다.
- 계약을 바꾸는 PR은 그 계약을 호출하는 쪽 담당자의 리뷰를 받습니다(MUST).
  호출하는 쪽 수정은 같은 체인 안에서 함께 머지합니다.

근거: 세 사람이 각자 mock으로 병렬 개발하므로, 계약이 어긋나면 통합할 때 한꺼번에 깨집니다.

### III. 데이터 정직성 (NON-NEGOTIABLE)

- `AGENTS.md`의 "반드시 지킬 것" 8개 규칙을 지킵니다. 핵심은 다음과 같습니다.
  - 날짜는 KST로 구합니다.
  - 모르는 값은 `null`로 둡니다.
  - 외부 응답이 비면 "전부 삭제"로 해석하지 않습니다.
  - 배치는 한 건의 실패를 격리하고, 실패가 많으면 0이 아닌 종료 코드로 끝냅니다.
  - 비밀값은 코드, 로그, DB에 남기지 않습니다.
- 일부 기간만으로 계산한 집계는 값으로 내보내지 않고 `null`로 둡니다(MUST).
- 시점 기준 조회는 그 시점에 공개되지 않은 정보를 쓰지 않습니다(MUST).
- 조회 실패를 "데이터 없음"으로 바꿔 돌려주지 않습니다(MUST). 실패는 실패로 알립니다.

근거: 토론의 근거와 수치가 틀리면 서비스의 핵심 가치인 신뢰가 무너집니다.
이번 데이터 체인 리뷰에서 머지 전 수정 항목 대부분이 이 원칙 위반이었습니다.

### IV. 근거와 고지 (가드레일)

- 사용자에게 보이는 모든 주장에는 출처를, 모든 수치에는 기준일(`as_of`)을 붙입니다(MUST).
- 다음은 0건이어야 합니다(MUST).
  - 투자 권유로 읽히는 표현과 적합·부적합 판정 노출
  - 임시값(`source=placeholder`)이나 검수되지 않은 관계의 노출
  - 분석 이벤트에 질문 원문, 온보딩 답변, 성향을 담는 것
- 사실과 관계 탐색 결과는 투자 성향에 따라 바꾸지 않습니다. 성향은 확인 포인트 강조에만 씁니다.

근거: PRD 3.3 가드레일 지표와 기능 명세서 7장(금융 표기와 고지)입니다.

### V. 수치로 채택한다 (Measure, then Adopt)

- 프롬프트, 검색, 모델, 청킹처럼 응답 품질에 영향을 주는 변경은 같은 평가셋으로 이전 버전과 비교한
  수치를 PR에 붙여야 머지할 수 있습니다(MUST). 자세한 절차는 `docs/CONVENTIONS.md`의 실험 변경 기록을 따릅니다.
- MVP 범위에 넣은 기능은 시연에서 실제로 동작해야 합니다. 품질이 부족하면 기능을 끄지 않고 일정을 조정합니다.

근거: 이 리빌드의 목표는 "숫자로 증명하는 리빌드"입니다.

## 문서 체계와 우선순위

SDD의 각 단계를 우리 문서에 대응시키면 아래와 같습니다.

| SDD 단계 | 우리 문서 | 위치 |
| --- | --- | --- |
| 헌법 | 이 문서, `AGENTS.md`, `docs/CODE_CONVENTIONS.md`, `docs/ENVIRONMENT.md` | 저장소 |
| 명세 (무엇을, 왜) | PRD, 기능 명세서(FN-ID, Given/When/Then 인수 조건) | 노션 할일 → PRD |
| 명세 (에이전트 단위) | 에이전트 기획서(토론, 온톨로지, 데이터, 시뮬레이션) | 저장소 `specs/` (Markdown) |
| 계획 (어떻게) | 멀티에이전트 설계 최종 확정, MVP Design Doc, ADR, `openapi.yaml` | 노션, 저장소 |
| 작업 | GitHub 이슈. 제목이나 본문에 FN-ID 또는 명세 경로를 적음 | GitHub |
| 구현 | PR | GitHub |

- 저장소의 명세는 Markdown으로 씁니다. HTML이나 이미지만으로 된 명세는 줄 단위 리뷰가 안 되고,
  AI 에이전트가 읽기도 어렵습니다.
- 여러 PR로 나뉘는 기능은 `specs/<번호>-<이름>/`에 `spec.md`, `plan.md`, `tasks.md`를 둡니다(`/speckit-specify`로 시작).
  작은 버그 수정이나 한 PR로 끝나는 변경은 이슈만으로 충분합니다.

**문서끼리 충돌할 때의 우선순위** (위가 우선)

1. 이 헌법
2. 채택된 ADR (같은 주제라면 최신 것)
3. PRD
4. 기능 명세서
5. 멀티에이전트 설계 최종 확정, MVP Design Doc
6. 에이전트 기획서
7. 코드

- 충돌을 발견하면 아래 문서를 따르지 말고 바로 고칩니다.
  - 아래 문서를 위 문서에 맞게 고치거나
  - 위 문서를 바꿔야 한다면 ADR을 씁니다.
- 날짜가 더 최근인 팀 결정이 있으면 그 결정을 ADR로 남긴 뒤 문서를 정리합니다.

## 개발 흐름과 리뷰·승인 기준

**흐름**

1. 명세: 무엇을, 왜. 모호한 점은 `/speckit-clarify`로 먼저 정리합니다.
2. 계획: 어떻게. 계약과 ADR을 바꾸는 일은 여기서 결정합니다.
3. 작업: 이슈로 나눕니다.
4. 구현: PR
5. 리뷰
6. 머지

**PR 본문 필수 항목**

- 연결된 명세: FN-ID, 명세 경로, 또는 ADR 번호
- 이 PR이 충족하는 인수 조건
- 명세와 다르게 구현한 부분과 그 이유. 없으면 "없음"
- 검증 방법과 결과

**리뷰 순서**

1. 명세 연결이 있는가
2. 인수 조건이 충족되는가. 조건마다 테스트나 재현 가능한 검증이 있어야 합니다.
3. 헌법 원칙 I~V 위반이 없는가
4. ADR과 API 계약에 맞는가
5. 정확성과 데이터 안전
6. 그 외 품질

**지적 수준과 처리**

| 수준 | 해당하는 경우 | 처리 |
| --- | --- | --- |
| 머지 전 수정 | 인수 조건 미충족 · 명세를 고치지 않은 채 명세·계약과 다름 · 원칙 III·IV 위반 · 데이터 손상 · 보안 · 사용자에게 보이는 오류 | Request changes. 고칠 때까지 머지하지 않음 |
| 고치면 좋음 | 위에 해당하지 않는 정확성·설계 개선 | 승인. 작성자가 후속 이슈를 만들고 PR에 링크 |
| nit | 취향, 표현, 사소한 정리 | 승인. 반영은 작성자 선택. 댓글에 `(nit)` 표시 |

**승인과 머지**

- "머지 전 수정"이 0건이고 승인이 1명 이상이면 머지할 수 있습니다. 머지는 작성자가 합니다.
- 명세 PR의 승인자
  - 무엇을, 왜 만드는지: PM(태은)
  - 구현이 가능한지: 해당 영역 구현 담당자
- 쌓인 PR(stacked PR)의 규칙
  - 중간 PR을 고치지 않고, 맨 위에 수정 PR을 하나 더 얹을 수 있습니다.
  - 이때는 체인 전체를 한 번에 머지하고, 머지가 끝나기 전에는 배치나 배포를 돌리지 않습니다.
- 리뷰 요청을 받으면 24시간 안에 첫 반응을 남깁니다.

## Governance

- 이 헌법은 다른 팀 관행보다 우선합니다. `AGENTS.md`, `docs/CONVENTIONS.md`, `docs/CODE_CONVENTIONS.md`는
  이 헌법 아래의 세부 규칙입니다. 서로 어긋나면 이 헌법에 맞춰 고칩니다.
- 개정은 PR로만 하고, 팀원 3명 모두가 승인해야 합니다.
- 버전은 semantic versioning을 따릅니다.
  - MAJOR: 원칙을 없애거나 의미를 바꿈
  - MINOR: 원칙이나 섹션을 추가함
  - PATCH: 문구를 다듬음
- 모든 PR 리뷰는 "리뷰 순서" 3번에서 헌법 준수를 확인합니다.
- 범위·일정 점검일(12/6)에 이 헌법이 실제 리뷰에 맞게 작동했는지 함께 돌아봅니다.
