## 브랜치

`main` 하나를 보호 브랜치로 두고, 모든 작업은 브랜치를 새로 파서 진행합니다.

```
<타입>/<로드맵ID 또는 범위>-<짧은 설명>
```

| 타입 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat/4.1-golden-queryset` |
| `fix` | 버그 수정 | `fix/debate-json-parse` |
| `refactor` | 동작 변경 없는 구조 개선 | `refactor/retriever-interface` |
| `exp` | 실험·평가 (채택 전) | `exp/2.1-table-chunking` |
| `docs` | 문서 | `docs/conventions` |
| `chore` | 설정·빌드·의존성 | `chore/ci-workflow` |

- 로드맵 항목이 있는 작업은 브랜치 이름에 ID(`4.1`, `2.3`)를 넣습니다. 나중에 무엇을 하던 브랜치인지 바로 보입니다.
- 브랜치는 병합 후 삭제합니다.
- `main`에 직접 push하지 않습니다.

## 커밋 메시지

Conventional Commits를 쓰되 본문은 한국어로 씁니다.

```
<타입>: <무엇을 바꿨는지 한 줄>

왜 바꿨는지, 어떤 선택을 했는지. 필요할 때만 씁니다.
수치가 있으면 여기에 적습니다. (Recall@5 0.62 → 0.71)
```

타입은 브랜치와 같은 집합(`feat` `fix` `refactor` `exp` `docs` `chore` `test` `perf`)을 씁니다.

```
feat: 리포트 표 영역을 별도 청크로 분리

pdfplumber로 표를 먼저 추출한 뒤 섹션 헤더 기준으로 청킹.
목표주가 표가 행 중간에서 잘리던 문제가 사라짐.
골든셋 Recall@5 0.62 → 0.71
```

- 한 커밋은 한 가지 변경만 담습니다. 포매팅과 로직 변경을 섞지 않습니다.
- 제목은 50자 안쪽, 마침표 없이, 명령형 대신 "~함/~추가" 형태로 통일합니다.

## 이슈

작업은 이슈에서 시작합니다. 템플릿 4종이 있습니다.

| 템플릿 | 쓰는 때 |
| --- | --- |
| 작업 | 로드맵 항목 구현, 기능 추가 |
| 버그 | 동작하지 않는 것 |
| 실험·평가 | 프롬프트·청킹·모델·검색 방식 비교 |
| 문서 | README, 컨벤션, 설계 기록 |

제목 규칙

```
[로드맵ID] 무엇을 할 것인지
```

예: `[4.1] 골든 쿼리셋 100개 구축`, `[3.4] Solar JSON 스키마 강제 적용`. 로드맵에 없는 작업은 ID 없이 `[기타]`로 씁니다.

- 담당자와 라벨을 함께 지정합니다. 담당자가 정해지지 않은 이슈는 `담당자확인` 라벨을 붙여둡니다.
- 하나의 이슈는 하나의 PR로 닫힐 만한 크기로 쪼갭니다. 이틀 이상 걸릴 것 같으면 더 쪼갭니다.

## Pull Request

제목은 커밋 메시지와 같은 형식을 씁니다.

```
feat: 리포트 표 영역을 별도 청크로 분리
```

본문에는 템플릿에 따라 아래를 채웁니다.

- **변경 요약** — 무엇이 달라지는지 1~3줄
- **변경 이유** — 어떤 이슈에 대응하는지
- **검증** — 실행한 명령어와 결과. 평가가 있는 변경이면 수치 비교
- **리뷰 포인트** — 특히 봐줬으면 하는 부분
- **남은 작업** — 이번 PR에서 다루지 않은 것
- `Closes #이슈번호`

규칙

- PR 하나는 되도록 400줄 이하로 유지합니다. 커지면 리뷰가 형식적으로 변합니다.
- 작업 중에도 방향 확인이 필요하면 Draft로 먼저 엽니다.
- 병합은 **Squash merge**를 씁니다. `main` 히스토리는 PR 단위로 읽힙니다.
- 병합 후 브랜치를 삭제합니다.
- 본인 PR을 본인이 승인할 수 없습니다. 리뷰어 1명의 승인이 필요합니다.

## 리뷰

- 리뷰 요청을 받으면 **24시간 안에** 첫 반응을 남깁니다. 당장 못 보면 언제 볼지 댓글로 남깁니다.
- 반드시 고쳐야 하는 것과 취향인 것을 구분해서 적습니다. 취향 제안에는 `(nit)`을 붙입니다.
- 코드가 아니라 코드의 선택에 대해 씁니다. "왜 이렇게 했는지" 묻는 질문은 언제든 괜찮습니다.
- 승인 후 병합은 PR 작성자가 합니다.

## 실험 변경 기록

검색·프롬프트·모델·청킹처럼 **응답 품질에 영향을 주는 변경**은 수치 없이 병합하지 않습니다.

1. 같은 평가셋으로 이전 버전과 새 버전을 돌립니다.
2. PR 본문 검증 항목에 비교표를 넣습니다.

   | 지표 | 이전 | 이후 |
   | --- | --- | --- |
   | Recall@5 | 0.62 | 0.71 |
   | nDCG@10 | 0.55 | 0.63 |

3. 채택·롤백 여부를 팀 실험 로그에 기록합니다.
4. 수치가 나빠졌다면 롤백도 결과입니다. 왜 기대와 달랐는지 한 줄 남기고 닫습니다.

## 완료 기준

PR을 열기 전 스스로 확인합니다.

- [ ] 변경한 영역의 테스트와 빌드가 통과한다
- [ ] 새로 추가한 동작에 테스트가 있다
- [ ] `.env`, API 키, 수집한 원본 데이터가 커밋에 포함되지 않았다
- [ ] 사용자가 누를 수 있는 버튼은 실제로 동작한다. 미구현이면 비활성 또는 '준비 중'으로 표시했다
- [ ] 품질에 영향을 주는 변경이면 평가 수치를 첨부했다
