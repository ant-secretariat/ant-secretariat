01

온톨로지 포지셔닝

왜 온톨로지인가 — RAG의 한계를 넘어 관계 기반 추론으로

"온톨로지는 검색이 아니라 실행이어야 합니다" — 에이전트가 지식 그래프를 탐색해 인과 체인을 구성하고, 그 경로 자체가 논거가 된다. 하네스(프롬프트 골격 + 도메인 컨텍스트 + 골든셋)는 도메인의 자산이 아니라 플랫폼의 자산이다.

핵심 원칙

기존 방식
RAG 검색 → 관련 청크 반환 → LLM이 알아서 추론. "기준금리가 삼성전자에 미치는 영향"을 직접 언급한 청크가 없으면 답 못 함.
온톨로지 방식
사전 정의된 노드·엣지를 따라 기준금리 → 반도체 섹터 멀티플 압축 → 삼성전자 밸류에이션 하락 경로를 구성. 청크가 없어도 관계에서 논거의 뼈대를 만든다.
핵심 차이
RAG는 "이미 쓰여진 것"을 찾는다. 온톨로지는 "관계에서 새로운 논거"를 만든다.

설계 방향

구분내용이유
채택온톨로지 = 실행 — 에이전트가 지도를 따라 논거 구성RAG 단독으로는 관계 기반 추론 불가
채택골든셋 자가 검증 + 켬/끔 비교쓰는 양이 아니라 효과로 평가
채택하네스 구조 (프롬프트 골격 + 도메인 컨텍스트)precheck 아젠다 사전과 같은 AgendaId 체계 공유
제외Text-to-SQL (정형 DW 쿼리)수치는 시맨틱 레이어 get_metric이 단일 정의로 계산
제외별도 그래프 DB 상시 운영T1 100종목·깊이 2 규모에서 이득이 작고 동기화 비용이 큼 (08)
차별점투자 도메인 관계 추론금리·환율 → 섹터 밸류에이션 경로. 금융 인과 체인 특화
차별점아젠다 연동 온톨로지탐색 경로가 아젠다별로 정의되어 Bull/Bear 논거 구성에 직결
차별점사실 층 / 판단 층 분리탐색 결과는 성향과 무관하게 동일. 성향은 Judge의 points_to_check·caution 강조에만 반영

전체 아키텍처

온톨로지는 도구 레지스트리 뒤의 "관계 사전"으로 연결됨. 에이전트는 직접 import하지 않음.

입력
사용자 질의 → EntityResolution → PrecheckResult
precheck 키워드 사전과 온톨로지 아젠다 경로가 같은 AgendaId를 씀
FLAG
기능 플래그 확인
관계 종류 × 에이전트 단위. 꺼져 있으면 호출하지 않음(기본값)
ONTO-A
컨텍스트 주입 (Phase A)
get_ontology_context(ticker, agenda_id) — 토론 job에서 아젠다별 1회 호출, 그래프 상태에 캐시
BULL·BEAR
같은 컨텍스트를 공유
입장별 필터링 없음. Bull은 강세 쪽, Bear는 약세 쪽 해석을 하도록 프롬프트로 역할만 구분
ONTO-B
추론 경로 생성 (Phase B)
get_reasoning_path(ticker, agenda_id) — 방향(positive/negative)이 붙은 경로 전체를 반환하고, 어떤 경로를 논거로 쓸지는 Bull·Bear가 선택
JUDGE
경로 일치 확인
Claim이 인용한 경로가 실제 엣지와 맞는지, 근거 앵커가 있는지 확인. 성향으로 채점을 바꾸지 않음
검증
관계 정확도·추론 체인 평가 + 켬/끔 비교

엣지 설계

관계 유형 7종 — 방향성 있는 경로의 기반

COMPANY──BELONGS_TO──▶SECTOR단방향
종목이 속한 섹터. 섹터 특성을 종목에 상속.
SECTOR / COMPANY──SENSITIVE_TO──▶MACROweight −1.0~+1.0 · source · window · as_of
상관 기반 민감도(일별 수익률과 코스피·환율·국채금리의 단순회귀 표준화 계수). 인과로 표현하지 않음. 실제 계수 전까지 source="placeholder".
ISSUE──BENEFITS──▶COMPANY / SECTORstrength low·mid·high
이슈 발생 시 수혜 종목·섹터.
ISSUE──HURTS──▶COMPANY / SECTORstrength low·mid·high
이슈 발생 시 타격 종목·섹터.
COMPANY──COMPETES_WITH──▶COMPETITOR양방향 · overlap 0~1
경쟁 관계. 직접 경쟁(1.0) ~ 간접 경쟁(0.3).
MACRO──IMPACTS──▶MACROdirection
매크로 지표 간 관계. 예: 기준금리 → 원/달러 환율.
COMPANY──EXPOSED_TO──▶ISSUEexposure 0~1
종목이 특정 이슈에 노출된 정도.

05

실행 계층 설계

A: 컨텍스트 주입 → B: 추론 경로. 두 함수 모두 레지스트리 도구로 노출되고 성향·입장 인자가 없음.

# Phase A — 컨텍스트 주입
def get_ontology_context(
    ticker: str,
    agenda_id: AgendaId,     # 공용 열거형 import, 문자열 하드코딩 금지
    depth: int = 2,
) -> OntologyContext

class OntologyContext(BaseModel):
    ticker: str
    agenda_id: AgendaId
    key_relations: list[Relation]          # 엣지 + source(placeholder/regression/manual)
    macro_exposures: list[MacroExposure]   # 상관 기반 민감도 + window·as_of
    related_issues: list[IssueRef]         # 유효 기간 안의 이슈만, evidence_chunk_ids 포함
    competitors: list[CompetitorRef]
    path_summary: str                      # 프롬프트 앞단 한 줄 요약
    graph_version: str                     # 평가 재현성

# Phase B — 추론 경로
def get_reasoning_path(ticker: str, agenda_id: AgendaId) -> list[ReasoningPath]

class ReasoningPath(BaseModel):
    steps: list[PathStep]
    direction: Literal["positive", "negative", "mixed"]   # Bull·Bear가 이걸 보고 선택
    chain_summary: str                     # "금리 상승 → 멀티플 압축 → PER 하락"
    evidence_anchors: list[str]            # 단계별 근거 chunk_id
    evidence_coverage: float               # 근거 있는 단계 ÷ 전체 단계

class PathStep(BaseModel):
    from_node: str; relation: str; to_node: str
    weight: float | None                    # 상관 기반 민감도
    direction: Literal["positive", "negative", "neutral"]
v1.2 변경: get_reasoning_path에서 stance 인자를 뺌. 입장별로 다른 경로를 계산하면 Bull과 Bear가 서로 다른 사실 위에서 토론하게 되어 "탐색 결과 공유·입장별 필터링 없음" 원칙과 충돌함. 방향 라벨이 붙은 경로 전체를 같이 받고 선택만 각자 함.

07

온톨로지 평가 체계

많이 넣고 많이 쓰는지가 아니라, 켰을 때 토론이 실제로 나아지는지로 평가.

기능 플래그

단계동작넘어가는 조건
off 기본값호출하지 않음해당 관계의 데이터 준비 완료(placeholder 아님)
shadow호출·로그만, 프롬프트에 주입하지 않음관계 정확도셋 통과, 지연·비용 증가 허용 범위
on프롬프트에 주입토론 루브릭셋 관계 질문 하위셋에서 켬/끔 블라인드 비교로 개선 확인

단위는 관계 종류 × 에이전트 (예: 토론 에이전트의 SENSITIVE_TO만 on). 설정은 코드의 플래그 테이블 한 곳에서 관리.

평가셋

평가셋내용지표목표
관계 정확도셋정답 엣지 vs 탐색된 엣지. 예: 삼성전자–금리 관계 방향엣지 방향 정확도≥ 90%
추론 체인셋정답 인과 체인 vs 생성된 체인 (Phase B)체인 단계 일치율≥ 70%
켬/끔 비교토론 루브릭셋의 관계 질문 하위셋, 같은 질문·근거로 블라인드 채점루브릭 점수 차이 · 비용·지연 증가개선 확인 시에만 on

품질 지표

지표정의목표
노드 커버리지T1 종목 중 COMPANY 노드가 있는 비율Phase A 시작 시 100%
placeholder 비율SENSITIVE_TO 중 source="placeholder" 비율0%가 되어야 플래그 검토 시작
evidence_coverage경로 단계 중 근거 앵커가 붙은 비율 (Phase B)측정 후 기준값 설정
삭제 유지: 경로 포함률·context 활용률·노드당 엣지 수는 많이 쓸수록 점수가 오르는 지표라 사용하지 않음.
