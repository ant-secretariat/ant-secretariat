# 0014. 사용자당 진행 중 job은 종류를 합쳐 1개이고, DB 부분 유니크 인덱스로 강제한다

- 상태: 채택 (토론 QA 후 재검토, #92)
- 결정일: 2026-11-24
- 결정자: 태은
- 의견을 준 사람: 수경 (합쳐 1개 제안, PR #68)
- 출처: PR #68 리뷰, MVP Design Doc v1.5 4.5

## 배경

한 사용자가 토론·시뮬레이션을 동시에 여러 개 돌리면 LLM 비용과 워커 슬롯을 혼자 차지합니다. 0012의 큐는 **모든 사용자의 job이 함께 들어가는 하나의 대기열**이라, 사용자별 제한은 큐가 아니라 job을 만드는 시점에 걸어야 합니다. 두 요청이 동시에 와도 하나만 통과해야 합니다.

## 선택지

**한도**
- **A. 종류 합쳐 1개** — 토론이 도는 동안 시뮬레이션도 409
- **B. 종류별 1개씩** — 토론 1 + 시뮬레이션 1 동시 가능

**강제 방법**
- **애플리케이션에서 세고 넣기** — "진행 중 개수 조회 → 0이면 insert" 사이에 다른 요청이 끼어들 수 있음
- **DB 부분 유니크 인덱스** — DB가 insert 순간에 강제

## 결정

**A + 부분 유니크 인덱스.**

```sql
create unique index agent_jobs_one_active_per_user
  on agent_jobs (user_id)
  where status in ('queued', 'running');
```

- **`job_id`가 아니라 `user_id`에 거는 이유:** `job_id`는 PK라 이미 행마다 달라서 사용자별 개수를 전혀 제한하지 못합니다. 막고 싶은 것은 "같은 `user_id`가 진행 중인 행에 두 번 나타나는 것"입니다.
- **조건(`where`)을 붙이는 이유:** 조건 없이 `user_id`에 유니크를 걸면 사용자가 평생 job을 하나만 만들 수 있습니다. 조건에 맞는 행(진행 중)만 검사 대상이라, 끝난 job은 몇 개든 남고(토론 내역) job이 `completed`·`failed`가 되는 순간 검사에서 빠집니다.

| job_id | user_id | status | 검사 대상 |
| --- | --- | --- | --- |
| D1 | u1 | completed | 아니요 |
| D2 | u1 | running | 예 |
| (새 요청) D3 | u1 | queued | 예 → D2와 겹쳐 insert 실패 → 409 `concurrent_job_limit` + `view_existing_job` |

- 한 사용자에게 D1·D2·S1이 동시에 대기하는 일은 생기지 않습니다. 진행 중 job이 있으면 두 번째 요청부터 409이고 FE가 진행 중인 job으로 안내합니다.
- 큐 안의 "먼저 들어온 순서"(0012)는 여러 사용자 사이에 적용됩니다.

| 막는 수단 | 막는 것 | 시점 |
| --- | --- | --- |
| 부분 유니크 인덱스 (이 ADR) | 한 사용자가 job을 여러 개 동시에 만드는 것 | API가 job을 만들 때 |
| `FOR UPDATE SKIP LOCKED` (0012) | 워커 여럿이 같은 job을 동시에 꺼내는 것 | 워커가 꺼낼 때 |

- 사용자당 하루 토론 10건(429 `rate_limited`, Design Doc 4.5)은 별도 규칙입니다.

## 영향

- **쉬워지는 것:** 비용·부하 상한이 사용자당 1개로 단순하고, 경쟁 조건 없이 DB가 보장합니다.
- **감수하는 것:** 토론이 도는 동안 이전 토론의 시뮬레이션을 동시에 돌릴 수 없습니다.
- **다시 볼 조건:** 토론 QA에서 이 제한이 불편하면 B(종류별 1개)로 바꾸고 이 ADR을 새 ADR로 대체합니다(#92). 바꾸는 비용은 인덱스를 `(user_id, job_type)`으로 바꾸는 한 줄입니다.
- **바꿔야 하는 것:** `agent_jobs` 마이그레이션의 인덱스, API의 insert 실패 → 409 변환(구현 계획 PR-2·PR-4).
