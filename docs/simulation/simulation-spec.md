## 1. 역할

**토론이 끝난 종목의 30일 뒤 주가가 어느 범위에 있을 가능성이 높은지 보여 주고, 금리·환율이 바뀌면 그 범위가 어떻게 달라지는지 보여 줍니다.**

- 가격을 "맞히는" 에이전트가 아닙니다. 30일 뒤 평균 방향은 학계에서도 잘 예측되지 않아서, **범위와 위험을 정직하게** 보여 주는 데 집중합니다.
- 평균 수익률은 예측하지 않고 0으로 고정합니다.

```text
토론 job 완료 (시뮬레이션 가능 여부 기록)
   └─ 사용자가 버튼을 누름
         ├─ 할 수 없는 종목 → 거절 (작업을 만들지 않음)
         └─ 시뮬레이션 job 생성
               ├─ 토론 결과에서 매크로·리스크 아젠다 꺼내기
               ├─ 리스크 분류(LLM): 토론 내용 → "금리 상승" 같은 시나리오
               ├─ 30일 가격 경로 1,000개 이상 생성
               ├─ 시나리오(what-if) 반영
               └─ 결과 요약 저장 → 화면 표시
```

## 2. 모델: GJR-GARCH + FHS

### 2-1. 하는 일

| 단계 | 내용 | 누가 |
| --- | --- | --- |
| 1. 변동성 모형 맞추기 | 과거 일별 수익률로 "변동성이 시기마다 커졌다 작아지고, 하락할 때 더 커지는" 패턴을 학습 | 데이터 파이프라인(매달 1일), `sim_params`에 저장 |
| 2. 잔차 모으기 | 변동성 효과를 걷어내고 남은 "예상 밖의 움직임"을 모음 | 데이터 파이프라인, 1단계와 함께 저장 |
| 3. 출발점 갱신 | 적합한 날부터 토론 기준일까지의 실제 수익률로 변동성을 하루씩 다시 계산해, 경로의 출발 변동성을 토론 기준일 기준으로 맞춤 | 시뮬레이션 에이전트(실행할 때) |
| 4. 경로 만들기 | 잔차를 무작위로 뽑아 하루씩 30번 이어 붙임. 매일 변동성을 다시 계산 | 시뮬레이션 에이전트(`simulate_paths` 사용) |

**출발점 갱신 (계수는 매달, 출발점은 실행할 때)**
- 계수(omega·alpha·gamma·beta)와 잔차는 3년 치로 맞춘 값이라 한 달 사이에 거의 바뀌지 않습니다. 그래서 매달 1회 적합으로 충분합니다.
- 하지만 30일 범위는 출발 변동성에 크게 좌우됩니다. `sim_params.params_json.next_variance`는 적합한 날 기준이라, 그대로 쓰면 그사이 시장이 크게 움직였을 때 범위를 과소평가합니다.
- 그래서 시뮬레이션할 때 적합일(`sim_params.as_of`) 다음 거래일부터 토론 기준일까지의 실제 수익률 r로 분산 식을 하루씩 굴려 출발점을 다시 계산합니다.
  - σ²(t+1) = ω + (α + γ·하락일) · r(t)² + β · σ²(t), 시작값은 `next_variance`, 평균은 0으로 고정
- 최대 20여 번 반복하는 계산이라 가볍고, 시세는 시뮬레이션 묶음으로 어차피 받아 옵니다. 매일 다시 적합하는 것보다 DB 용량(1년 약 115MB → 약 5.5MB)과 수렴 실패 변동 면에서 낫습니다.
- 따로 붙은 이름은 없고, GARCH를 쓸 때 흔히 하는 "계수 고정 + 필터 갱신"입니다.

### 2-2. 왜 이 모델인가

| 이유 | 근거 |
| --- | --- |
| 주식 변동성의 특성(몰려서 나타남, 하락 때 커짐)에 맞음 | Hansen & Lunde 2005: 개별 주식에서 비대칭 항이 있는 모델이 기본 GARCH보다 나음 |
| 큰 손실 위험 추정에 오래 쓰인 방법 | Kuester 등 2006: NASDAQ 표본 밖 VaR 비교에서 FHS 변형이 상위권 |
| 여러 날 위험 추정에서 선호됨 | Ruiz 2023: 10일 VaR에서 GJR 모형을 하루씩 반복하는 방식이 대체로 선호됨 |
| 대규모 비교에서 딥러닝이 못 이김 | MDPI *Econometrics* 2026: 39개 증시, 2005–2025 비교에서 LSTM이 GARCH-FHS를 못 이김 |
| 가볍고 설명하기 쉬움 | 모델이 숫자 몇 개라 요청 중에 학습할 필요가 없음 |

**한계**
- 개별 종목의 30일 분포를 직접 비교한 문헌은 찾지 못했습니다. **"가장 좋은 모델"이 아니라 "기본값으로 방어 가능한 모델"** 입니다.
- 국면이 갑자기 바뀔 때(2020년 코로나) 변동성을 과소평가한 사례가 있습니다. 시세가 3년 치라 그런 구간이 적합 기간에 없고, 평가 결과에 "최근 3년 수준의 변동성에서만 검증됨"이라고 밝힙니다.

### 2-3. 왜 LSTM이 아닌가

| 이유 | 내용 |
| --- | --- |
| 데이터 부족 | 종목 하나로는 겹치지 않는 30일 구간이 약 25–40개뿐 |
| 전 종목 합치기도 어려움 | 시세가 핵심 종목 100개에만 있고, 상장폐지 종목 이력이 없어 하방 위험을 과소평가할 수 있음 |
| 증거와 비용 | 데이터가 충분한 비교에서도 LSTM이 이기지 못했고, 전 종목 학습은 서빙 인프라 비용이 큼 |

### 2-4. 지금 코드(LSTM)와 비교

| 항목 | 지금 LSTM | GJR-GARCH + FHS |
| --- | --- | --- |
| 학습 데이터 | 30일 구간 약 25–40개 | 일별 수익률 약 740개 전부 |
| 맞히는 것 | 30일 뒤 평균 수익률과 폭 | 변동성 패턴(평균은 0으로 고정) |
| 30일 경로 | 변동성 고정, 정규분포 | 매일 변동성이 바뀌고 큰 움직임 반영 |
| 저장 | 신경망 가중치 파일 | `sim_params`의 숫자 몇 개와 잔차 |
| 적합 시점 | 요청할 때(최대 50에폭) | 계수는 매달 1일 미리, 출발 변동성은 실행할 때 토론 기준일까지 갱신 |

### 2-5. 시나리오(what-if) 계산

| 단계 | 방식 |
| --- | --- |
| 민감도 | `sensitivities` 표의 30일 베타. 코스피·원/달러·국고채 3년을 **함께 넣은 회귀**라 환율·금리 효과에서 시장 전체 움직임이 이미 빠져 있음. 국고채 10년은 단독 회귀 |
| 충격 크기 | 그 지표의 과거 30일 변화 폭(1σ)의 1배·2배. 금리와 환율을 같은 잣대로 비교할 수 있음 |
| 결과에 반영 | 영향 = 베타 × 충격 크기. 30일 분포 전체를 그만큼 옮김 |
| 불확실성 | 베타의 95% 신뢰구간을 같이 냄. 0을 포함하면 **"방향이 불확실"** 로 표시 |
| 월별 지표 | 유가·소비자물가·D램 수출물가는 상관만 있고 베타가 없어서, 영향 크기는 내지 않고 **"같이 움직이는 경향"** 만 참고로 보여 줌 |

- 섹터 단위로 보면 금리·환율 영향은 시장 효과를 빼면 대부분 0에 가깝습니다. 종목 단위에서도 "방향 불확실"이 많이 나올 수 있고, 그게 정직한 결과입니다.

## 3. 다른 에이전트와의 연결

### 3-1. 오케스트레이터

| 항목 | 내용 |
| --- | --- |
| job | 토론 job과 시뮬레이션 job을 나눔. 상태는 job마다 대기·실행 중·완료·실패 4가지 |
| 버튼 | `POST /orchestrate/debate/{job_id}/simulate`. 단일 종목 토론이 완료된 job만. 비교 모드면 409 |
| 미리 알려 주기 | 토론이 끝날 때 `simulation_ready`(시뮬레이션 가능 여부)를 같이 내려 줌. `false`면 버튼을 끄고, 눌러도 작업을 만들지 않고 `no_data`로 거절 |
| 시뮬레이션 job 기록 | 토론 job ID(`debate_job_id`)와 기준일(토론 job의 `data_as_of`). 같은 토론의 시뮬레이션 job이 진행 중이거나 끝났으면 그 job을 돌려줌(`reused=true`) |
| 시뮬레이션 가능 기간 | `sim_params` 과거값을 지우지 않으므로 시뮬레이션 쪽에서는 기간 제한이 필요 없음(5절). 기간은 토론 결과 보관과 DB 용량으로 오케스트레이터가 정함(#92) |
| 동시 실행 한도 | 토론과 시뮬레이션을 **합쳐서 사용자당 진행 중 작업 1개**(ADR 0014). 토론이 도는 동안 버튼을 누르면 409. 끝난 작업은 세지 않음 |
| 결과 저장 | 요약만 저장(분위수, 시나리오별 결과). 경로 전체는 저장하지 않음(DB 용량) |

### 3-2. 호출 모양

```python
async def run_simulation(
    ticker: str,
    user_id: str,
    debate_job_id: str,   # 토론 job. 토론 결과를 여기서 읽음
    as_of: str,           # 토론 job의 data_as_of. 모든 데이터 조회의 기준
    *, invoke,            # 도구 레지스트리 (데이터 조회)
) -> SimulationResult      # 결과만 돌려줌. 진행 이벤트·상태 전환은 작업 워커가 맡음
```

- 계약서는 아직 `run_simulation(ticker, user_id, job_id)`입니다. 이 모양(`debate_job_id`, `as_of`, 결과만 돌려줌)과 job 상태 4가지는 **계약 draft.6에서 바꿉니다.**
- 데이터는 도구 레지스트리로 조회합니다. 조회가 실패하면 "데이터 없음"으로 바꾸지 않고 실패로 처리합니다.
- `get_agent_context`는 `intent` 없이 부릅니다. 시세·지수·매크로 전체가 필요하기 때문입니다.
- 토론 결과에서 아젠다를 **순서가 아니라 ID로** 꺼냅니다. 아젠다 순서는 precheck 선택 순서라 매번 달라집니다.
- 시뮬레이션은 단일 모드 토론만 대상이라 단일 모드 결과(`DebateResult.agendas`)만 봅니다. 비교 모드(`comparison`)는 보지 않습니다.

```python
agendas = {a["id"]: a for a in load_debate_result(debate_job_id)["agendas"]}  # 토론 결과 AgendaResult.id
# 근거 부족 루프(#78)로 주장이 모두 빠진 아젠다는 없는 것과 같이 다룸
macro_agenda, risk_agenda = (a if a and a.get("claims") else None for a in (agendas.get("macro"), agendas.get("risk")))
```

| 상황 | 처리 |
| --- | --- |
| 매크로·리스크 중 하나 이상 있음(주장 1개 이상) | 있는 것만 리스크 분류에 넘김 |
| 둘 다 없음, 또는 아젠다는 있지만 주장(`claims`)이 0개 | 리스크 분류를 건너뛰고, 시나리오 없이 기본 분포만 제공 |

### 3-3. 실패

| `error_code` | 언제 |
| --- | --- |
| `insufficient_history` | 그 기준일의 파라미터가 없거나 정상이 아님(보통은 버튼 단계에서 미리 걸러짐) |
| `upstream_unavailable` | 데이터 조회 실패 |
| `internal_error` | 그 밖의 오류 |

- 실패하면 시뮬레이션 job만 실패로 끝나고, 토론 job은 완료 그대로입니다.

### 3-4. `tier`와 `data_tier`

- `tier`(T0/T1/T2)는 종목별 데이터 깊이, `data_tier`(리포트·뉴스 등)는 근거 종류입니다.
- 시뮬레이션은 둘 다와 상관없이 **그 기준일의 파라미터가 있으면** 실행합니다. 지금 파라미터는 핵심 종목(T1)에만 있습니다.

- **기준일 주의:** 파라미터는 매달 1일에 다시 맞추므로, 토론 기준일(`data_as_of`)과 같은 날짜의 파라미터는 보통 없습니다. **토론 기준일 이전 중 가장 최근 `as_of`** 의 파라미터를 씁니다. 계수는 최대 한 달 전 값이지만, 출발 변동성은 토론 기준일까지 갱신하므로(2-1절) 최근 움직임이 반영됩니다. 결과에는 파라미터 기준일과 토론 기준일을 함께 표시합니다.
- **보관 (#92):** `sim_params`는 적합할 때마다 기준일별로 쌓이고 지우지 않습니다. 그래서 오래된 토론도 그 시점의 파라미터로 다시 시뮬레이션할 수 있습니다.
  - 용량: 1회 적합(100종목)이 약 0.46MB, 11/24 기준 4회 적재로 표 전체 약 1.8MB입니다. 매달 1회면 1년에 약 5.5MB라 정리할 필요가 없습니다.
  - 다시 볼 조건: 시뮬레이션 대상을 전 종목(약 2,700개)으로 넓히면 1년에 약 150MB가 됩니다. 그때 Q5(DB 용량)와 함께 보관 기간을 정합니다.

## 6. 평가

시뮬레이션은 통계 계산 결과이고, 정답은 "실제 30일 뒤 가격"입니다. 사람이 라벨링할 필요 없이 과거 시세로 자동 계산합니다. 모델 순위를 매기지 않고, **보여 주는 범위가 정직한지**와 **고친 것이 실제로 반영됐는지**를 봅니다.

| 영역 | 지표 | 목표 | 방법 |
| --- | --- | --- | --- |
| 범위 정확성 | 90% 구간 적중률, 하방 5% 선 위반율 | 참고 범위 86–94%. 80% 미만이나 97% 초과면 실패로 보고 보정. 하방 위반율 10% 넘으면 하방 위험 과소평가로 점검 | 약 10개 종목, 과거 3년, 그 시점까지의 데이터만으로 예측(walk-forward) |
| 개선 확인 | **단순 기준선**(최근 변동성을 고정한 정규분포로 30일 범위를 그림) 대비 구간 적중률, CRPS | 수치 그대로 기록 | 같은 종목·기간 1회 비교 |
| 시나리오 | 금리·환율을 바꾸면 결과가 실제로 달라지는지, 신뢰구간 표시 | 100% 통과 | 자동 테스트 |
| 데이터·재현성 | 이상 수익률(하루 ±30% 초과) 처리, 파라미터 없는 종목 거절, 같은 입력·seed면 같은 결과 | 100% 통과 | 자동 테스트 |
| 시점 | 토론 기준일 뒤 데이터가 섞이지 않음(출발점 갱신 포함) | 0건 | 자동 테스트 |
| 출발점 갱신 | 적합일과 토론 기준일이 같으면 갱신 결과가 `next_variance`와 같음, 큰 하락일이 끼면 출발 변동성이 커짐 | 100% 통과 | 자동 테스트 |
| 운영 | 응답 시간 p95, 실패율 | 기준선 측정 뒤 결정 | 자동 측정 |

- 종목당 겹치지 않는 30일 구간이 25–40개뿐이라 적중률에도 오차가 큽니다. 86–94%는 합격선이 아니라 참고 범위입니다.
- 1% 같은 극단 위험은 표본이 너무 적어 검증 기준으로 쓰지 않습니다.

- **비교 대상은 지금 LSTM이 아니라 단순 기준선입니다.** LSTM은 어차피 버릴 코드라 평가하려고 손보는 시간이 아깝고, 지금 LSTM 수치는 학습 데이터로 다시 평가한 값이라 기준으로 쓸 수 없습니다. 단순 기준선은 몇 줄로 만들 수 있고, "변동성이 매일 바뀌는 모델이 고정 변동성보다 범위를 더 정직하게 잡는지"를 보여 주기에 충분합니다.

**착수 순서**
1. 평가 도구(walk-forward)와 단순 기준선을 먼저 만들고, 기준선으로 도구가 제대로 도는지 확인합니다.
2. 시나리오 반영·재현성 자동 테스트를 만듭니다.
3. 에이전트를 새 방식으로 바꾸고 같은 도구로 기준선과 비교합니다. 이 비교표를 교체 PR에 붙입니다.

## 7. 지금 코드의 문제점 (LSTM 버전)

main의 에이전트 코드(`backend/agents/simulation/`)는 아직 v1입니다. 새 방식으로 바꾸면 아래가 함께 풀립니다.

| 문제 | 내용 | 영향 |
| --- | --- | --- |
| 시나리오가 반영되지 않음 | 금리·환율 값을 바꿔도 정규화 과정에서 다시 지워짐 | "금리가 오르면?"을 돌려도 결과가 같음 |
| 충격 크기 단위가 제각각 | 모든 지표에 "+1". 금리는 1%p, 환율은 1원 | 지표끼리 비교할 수 없음 |
| 해석 문구가 부정확 | −1.0 미만만 "손실 확대", 나머지는 전부 "영향 제한적" | 좋은 영향도 "제한적"으로 나옴 |
| 리스크 아젠다가 안 넘어옴 | 토론이 두 번째 아젠다만 넘김 | 리스크 논증이 버려짐 |
| 목표주가를 받고도 안 씀 | 담아 오기만 하고 사용하지 않음 | 쓸 방식이 정해지지 않음 |
| 성능 수치를 믿을 수 없음 | 학습에 쓴 데이터로 다시 평가 | 정확도가 실제보다 좋게 나옴. 그래서 새 모델 비교에도 쓰지 않음(6절) |
| 정성 리스크가 비어 있음 | `qualitative_risks = []` | 신제품 지연 같은 리스크가 안 보임 |
| 잠재 버그 | 경로 수를 바꾸면 잘못된 경로가 뽑힐 수 있음 | 지금 설정에서는 영향 없음 |

- `seed=42` 고정은 문제가 아닙니다. 기본 결과와 시나리오 결과가 같은 난수를 써서, 두 결과의 차이를 순수한 충격 효과로 볼 수 있습니다.
